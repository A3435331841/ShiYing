## 0. v0.3.0 追加改造（同日）

在第一轮修复之后，又做了一轮结构性改造，解决「单文件几千行」和「界面粗糙」两个问题，并关闭了剩余的重复提交、缓存、旧入口问题。

### 0.1 代码拆分

| 原文件 | 行数 | 拆分后 |
|---|---|---|
| `app/downloader.py` | 7,786 | `app/engine/`：common 971、core 294、discovery 547、naming 283、platform_items 922、transfer 1,512、douyin_probe 2,083、douyin_media 1,900 |
| `app/task_manager.py` | 3,889 | `app/manager/`：common 442、core 1,513、lifecycle 380、issues 246、douyin_profile 1,494、xiaohongshu 275 |

- 旧模块退化为兼容门面，`from app.downloader import MediaDownloader`、`from app.task_manager import DownloadManager` 以及测试里的 `monkeypatch.setattr("app.downloader.X", ...)` 全部继续可用（门面会把属性赋值镜像到各子模块）。
- 拆分后最大单文件 2,083 行，超过 2,000 行的只剩抖音探测模块（平台规则本身复杂）。
- 全量 1,878 项离线测试通过。

### 0.2 界面重做

- 首页改为「添加下载 → 平台 → 最近任务」三段式；侧栏显示缓存用量；状态改为带圆点的胶囊；进度条、搜索框、空状态、弹窗全部重写。
- 浅色与深色主题重新设计，实测对比度：浅色 4.73–17.1:1、深色 6.2–14.2:1；760 px 视口横向溢出 0；减少动画偏好继续生效。
- 任务行按平台显示左侧色条与平台色块，失败原因单行截断并可查看详情。

### 0.3 新功能

- **重复任务确认**：`GET /api/jobs/exists` 按平台与规范化来源匹配；创建前弹窗，可选「跳过这些链接」或「仍然下载」。真实浏览器验证：重复链接只弹一次确认，跳过后任务数不变。
- **缓存管理**：`GET /api/cache`、`POST /api/cache/clear`；设置中显示缓存大小/文件数，正在下载时拒绝清理（409），暂停或待验证任务清理前提示需要重新下载。
- **主页预览快速失败**：主页链接不再进入最长 4 分钟的同步预览，直接提示「请直接解析并下载」。
- **旧视频号入口停用**：`POST /api/wechat/jobs` 返回 410；历史记录仍可查看、取消、删除，重试统一走主队列。
- **删除死资源**：移除未引用的 `styles.css`（28 KB）与 `shiying.css`（2.5 KB）。

### 0.4 v0.3.0 验证

- 全量测试：1,878 项收集，退出码 0。
- 浏览器实测：1440 px 浅色/深色、760 px 浅色/深色截图；重复弹窗、设置缓存面板、搜索空状态均可用；控制台 0 错误。
- 版本与 build：`0.3.0`。

## 1. 结论

拾影从「演示可用」推进到「个人日常可用」：主流程（粘贴 → 预览 → 选集 → 下载 → 暂停/继续 → 重试 → 找到文件）在真实浏览器与真实 API 上跑通，P1 级缺陷全部关闭；v0.3.0 又完成了模块拆分与界面重做。
仍不建议对外宣称「所有平台所有作品可用」：真实平台样本与视频号登录态仍受账号、网络与平台边界限制，见第 7 节。

## 2. 改前实测（可复现）

1. 打开首页，粘贴 `https://www.bilibili.com/video/BV1xx411c7mD`，点「预览选集」。
   - 控制台：`Uncaught ReferenceError: $ is not defined`；`/api/preview` 请求数 0；预览弹窗不出现。
2. `home.js` 第 357 行 `initialize();` 之后是 `})();`，预览函数定义在闭包之外，却引用闭包内的 `$`、`state`、`api`、`extractShareLinks`。
3. 真实下载中点「暂停」→「继续」：当前项被标记 `cancelled`，`resume_job` 的目标集合不含 `cancelled`，当前文件被跳过。
4. `downloader.py` 视频号暂存文件为 `.{item.id}.checking.mp4`，同一作品跨任务同名，写入/发布/清理互相干扰。
5. `wechat.py` 仅在 `total` 非零时回调进度，未知总大小时既无进度也无法及时取消。
6. 所有请求共用 `AbortSignal.timeout(20000)`，与「扫码最长 5 分钟」和长主页预览冲突。
7. 桌面壳固定 `9016`，Web 入口固定 `8766`，两边互不识别。
8. `bilibili_opus.py` 把上游图片地址直接交给 `ydl.urlopen`，没有其他平台的逐跳白名单校验。
9. `_load_config()` 损坏时静默返回默认值；原文件被后续保存覆盖。
10. 任务列表每次进度变化整体替换 `innerHTML`，键盘焦点掉到 `body`。
11. 深色模式筛选文字 `#66738a` 对 `#17202d` 约 3.42:1；浅色辅助文字 `#768296` 对白约 3.89:1；页脚 10 px。
12. `pyproject.toml` 与 `requirements.txt`、`build_info.py`、README 四套版本/依赖事实；build 不含桌面入口。
13. `tests/test_preview.py` 通过真实 `main.manager` 写入 `data/state`，把假样本链接带进用户任务列表。

## 7. 明确未完成 / 仍存在的限制

以下不属于「这次没做完的修复」，而是产品级已知边界，不应用本次报告过度解读为已解决：

1. **真实账号与真实网络未复验**：抖音、快手、小红书、视频号、YouTube 的实际下载能力仍取决于账号、地区、风控与平台当前接口；本次只做了离线回归与 UI/API 实测。
2. **`app/static/app.js`（152 KB）仍被加载**：新界面只用其中的 `ShiyingRuntime` 文案本地化辅助函数，其余旧 UI 在 `data-ui="shiying"` 时直接返回。拆分需要迁移错误文案映射，风险高于收益，留作后续。
3. **视频号旧任务历史仍走独立存储**：`wechat.py` 的 `POOL/JOBS/CANCELLATIONS` 与 `data/wechat-jobs.json` 继续服务旧记录；新任务已统一走主队列，创建入口返回 410，但旧记录与主队列的并发上限、退出收尾仍未完全合并。
4. **平台承诺**：README 的长能力矩阵未逐条重写；本次只对齐了会误导操作的标题、Cookie 默认值、端口、版本与各平台入口。
5. **磁盘信息不完整**：设置里只显示缓存大小，没有显示下载目录占用与磁盘剩余空间。
