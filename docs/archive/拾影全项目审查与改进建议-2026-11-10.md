## 1. 结论与优先顺序

**拾影已有相当完整的下载底座，当前最需要解决的是新功能与既有底座之间的衔接。** 预览、选择分集、暂停恢复和扫码登录已经出现在界面上，但部分操作不能按用户理解完成。继续增加平台或按钮之前，先让这些常用动作可靠，能明显提高个人使用的便利性。

优先处理以下六件事：

1. **预览真正可点击，选择多少项就下载多少项。** 当前预览按钮报 JavaScript 错误；即使绕过按钮，选择结果也会在新任务启动时丢失。
2. **暂停后能接着完成当前文件。** 当前真实工作线程的暂停会把当前项目留在“已取消”，继续时跳过它。
3. **扫码登录的等待与取消完整一致。** 页面说可以等待五分钟，请求却在二十秒后中断；后台浏览器可能继续等待。
4. **视频号下载可取消，并隔离重复任务的临时文件。** 未知总大小的流不会触发用于取消检查的回调；两个相同作品任务会使用同一个暂存文件。
5. **启动、停止、安装只有一套权威规则。** 现在有 8766 与 9016 两条入口、多份不一致的依赖清单和版本信息。
6. **把真实用户操作变成发布门槛。** 大量单元测试通过，并不能证明“点预览 → 选择 → 下载”或“暂停 → 继续”这些组合流程可用。

不建议为此重写整个项目。保留 FastAPI、现有下载器和本地状态存储，优先修复跨模块的数据、状态和生命周期约定。

本次整理了 **15 项当前问题（6 项 P1、9 项 P2）**，每项包含证据、影响、最小修复方式和验收条件。最终代码快照全量测试结果为 **1827 通过、1 失败、18 跳过**；唯一失败属于测试访问本机活动服务造成的环境隔离问题，详细分析见第 11 节。额外操作链路复现发现的问题没有被这些现有测试覆盖。

## 4. 已定位的问题与具体修复建议

### F01 · P1 · “预览选集”点击后报错，用户得不到有效反馈

**证据：实测复现。** [home.js:357](<D:/Shiying/app/static/home.js:357>) 结束立即执行函数，`openPreview` 等三个函数却在其外部定义；它们引用的 `$`、`$$`、`state`、`api`、`extractShareLinks` 都定义在内部。

实际操作：等待页面显示“本地运行”，粘贴有效链接，点击“预览选集”。捕获到 `$ is not defined`，预览弹窗没有打开，`/api/preview` 请求数为 0。错误发生在函数的 `try` 之前，页面也没有解释发生了什么。

**最小修复：** 将预览相关状态、函数放回已有闭包，或明确传递依赖；无需为此引入前端框架。同时把点击入口纳入统一错误处理。

**验收：** 从真实首页点击预览，弹窗打开且没有未处理异常；失败时按钮恢复、输入保留、原因可见。

### F02 · P1 · 选择分集没有贯穿创建与启动，可能下载未选内容

**证据：实测复现。** [main.py:440](<D:/Shiying/app/main.py:440>) 只返回临时解析结果；[home.js:401](<D:/Shiying/app/static/home.js:401>) 随后创建 `auto_start=false` 的空任务，再发送所选 ID。[task_manager.py:842](<D:/Shiying/app/task_manager.py:842>) 仅在任务已经有 `items` 时应用选择；空任务进入重新发现分支，将 `targets` 设为 `None`。

本次通过真实 API 串联验证：预览返回两项 → 创建任务的 `items` 为 0 → 启动只选择 `part1` → 模拟引擎实际下载 `part1` 和 `part2`，最终标记完成。

还有两个相连问题：

- 即使任务预先存在两项、只下载其中一项，另一个标为 `skipped`，最终仍显示 `partial`。本次复现为 `completed + skipped`、计数 `1/2`，根因是 [task_manager.py:2296](<D:/Shiying/app/task_manager.py:2296>) 按全部项目判断完成。
- 输入多条链接时，[home.js:364](<D:/Shiying/app/static/home.js:364>) 静默取第一条，未明确告诉用户其余链接不在本次预览中。

**最小修复：** 让预览对应同一份待确认任务，确认时只启动该任务；或者在重新发现后保留并验证用户选中的稳定作品 ID。将“未选择”与“未完成”分开计数。多链接预览先明确只支持单条，避免悄悄忽略。

**验收：** 三集只选第二集，只有第二集进入下载器；任务显示“所选 1/1 已完成”，不是“部分完成”；全部不选不可启动；选择项消失时要求重新确认，不扩大下载范围。

### F03 · P1 · 真正下载中的任务暂停后，继续会跳过当前文件

**证据：实测复现。** [task_manager.py:1542](<D:/Shiying/app/task_manager.py:1542>) 捕获 `DownloadCancelledError` 时，先把当前项目标记为 `CANCELLED`。外层再调用 `_mark_paused_locked`，但其转换集合不包含已经取消的项目。[task_manager.py:930](<D:/Shiying/app/task_manager.py:930>) 恢复时也不选择 `CANCELLED`。

用实际线程与取消事件复现：下载已开始 → 请求暂停 → 任务为 `paused`、当前项目为 `cancelled` → 点击继续 → 当前项目没有再次进入下载，最终任务为 `partial`。

**最小修复：** 在首次处理取消异常的位置区分用户“暂停”与“取消”，保证任务及项目状态一致；恢复目标必须包含因本次暂停中断的当前项目。不要把所有历史取消项无条件重下。

**验收：** 覆盖正在读取文件、解析中、排队中和即将完成时的暂停；继续后完成当前所选内容，取消后不会自动恢复。所谓“断点续传”还需分别验证各平台的 Range、临时文件与续传策略，不能由状态切换测试推断。

### F04 · P1 · 登录和耗时预览共用二十秒请求超时，与功能约定冲突

**证据：源码确认。** [home.js:26](<D:/Shiying/app/static/home.js:26>) 所有请求统一使用 `AbortSignal.timeout(20000)`。[home.js:300](<D:/Shiying/app/static/home.js:300>) 告诉用户扫码最长等待五分钟；[wechat.py:444](<D:/Shiying/app/wechat.py:444>) 确实在同步 HTTP 请求里等待扫码。预览接口同样同步完成站点发现。

用户扫码超过二十秒或主页预览解析较慢时，前端先报超时，后台操作可能还在执行。再次点击登录可能产生新的窗口，用户也不知道第一次是否仍有效。预览暂时被 F01 挡住，修复 F01 后仍会遇到此问题。

**最小修复：** 请求支持按操作设置超时；登录按钮在同一次操作结束前不可重复启动，并提供取消。预览优先复用现有任务与 SSE 进度，让用户看到“正在读取第几页”，避免长时间悬挂的单次请求。

**验收：** 使用模拟的 30–60 秒延迟验证界面仍正确等待；取消后浏览器/解析工作收尾；超时后不会出现“前端失败但后台又保存成功”的无提示结果。

### F05 · P1 · 同一视频号作品的并发任务共用暂存文件

**证据：实测复现路径冲突，未制造真实媒体损坏。** [downloader.py:506](<D:/Shiying/app/downloader.py:506>) 的项目 ID 按平台与作品身份确定，相同作品跨任务相同；[downloader.py:4610](<D:/Shiying/app/downloader.py:4610>) 暂存文件只使用 `item.id`。主队列可以同时执行两个任务，当前创建接口也不按作品去重。

两个不同任务 ID 的相同作品同时进入下载方法，本次观察到两个工作线程得到同一个 `.checking.mp4` 路径；底层 `.part` 也随之相同。一个线程的写入、发布或 `finally` 清理可能干扰另一个。最终发布“不覆盖”的保护不能隔离此前的暂存阶段。

**最小修复：** 暂存路径使用已有 `_job_id` 与项目 ID，或 `mkstemp`，不要自建并发文件锁系统。同时为重复提交提供“查看已有任务 / 再次下载”的明确选择。

**验收：** 两个相同链接并发时临时路径不同；一个取消不影响另一个；已有文件保持不变；用户明确知道重复任务是复用、跳过还是另存。

### F06 · P1 · 视频号未知总大小时没有进度，也不能及时暂停或取消

**证据：实测复现。** [wechat.py:312](<D:/Shiying/app/wechat.py:312>) 只有 `total` 非零时才调用进度回调。新统一下载路径在 [downloader.py:4611](<D:/Shiying/app/downloader.py:4611>) 创建独立取消事件，仅通过这个回调把主任务的取消状态传入。

模拟没有 `Content-Length` 的五块响应，在第二块前发出取消：实际仍读取全部五块；进度事件为 0；主取消回调直到五块读完后才被检查。用户看到的是一直下载或停止无反应。

**最小修复：** 逐块检查主任务取消回调；无论总大小是否已知都报告已下载字节和速度。只有百分比、ETA 可以未知。读取超时也应有明确上限。

**验收：** 无 `Content-Length`、缓慢分块和中途断网均能显示真实已读字节；取消不需要等到完整文件传完。不要用“无总大小”作为不更新状态的理由。

### F07 · P2 · 两套启动入口使用不同端口，桌面入口不能复用现有后台

**证据：运行状态只读观察 + 源码确认。** README 与 `start.bat` 使用 8766；[launch_shiying.py:14](<D:/Shiying/launch_shiying.py:14>) 固定 9016，中文版停止脚本也固定 9016。审查时本项目服务确实在 8766 健康运行，9016 无服务。

桌面启动器只检查 9016，随后试图启动新的后端；项目级单实例锁又不允许为同一个项目再开一套后台。启动器仍等待 9016，可能把“已有服务在另一个合法端口运行”报成启动失败。

**最小修复：** 使用已有运行身份记录获取端口并校验项目与 build，所有入口复用同一后台。普通用户文档保留一个启动入口；旧脚本改为兼容转发。关闭窗口与完全退出的含义在窗口中说明，并提供可见的完全退出入口。

**验收：** 先用旧脚本启动，再打开桌面入口，立即显示同一个服务；停止入口操作同一实例；不会要求用户记住端口或手动杀进程。

### F08 · P2 · 新增 B站图文下载没有接入其他平台已有的媒体 URL 边界

**证据：模拟传输拦截复现；没有向内网发送请求。** [bilibili_opus.py:118](<D:/Shiying/app/bilibili_opus.py:118>) 将上游图片 URL 直接放入候选；[downloader.py:6544](<D:/Shiying/app/downloader.py:6544>) 对小红书、抖音和快手分别校验候选与跳转，但 B站进入 [downloader.py:6766](<D:/Shiying/app/downloader.py:6766>) 的直接 `ydl.urlopen` 分支。

将模拟 B站图片候选设为 `http://127.0.0.1:9999/audit`，该地址到达了被替换的传输层，未在调用前被拦截。真实利用需要上游响应出现恶意候选或跳转；本次没有证明平台正在返回这种地址。

**最小修复：** 给 B站图文补上与其他平台同等的可信媒体地址和逐跳校验，拒绝回环/私网目标、用户信息和异常端口。可信域名应来自实际平台素材证据，不按任意后缀放开。复用现有校验思路即可。

## 6. 后端、性能、数据与安全的维护建议

### 6.1 状态规则优先于新增抽象

建议用一张小表明确任务与项目的关系：排队、解析、下载、正在暂停、已暂停、正在取消、已取消、待登录、完成、部分完成、失败。明确哪些状态允许继续、重试、删除和退出收尾。

最值得固定的约束是：

- 用户选择的范围不会在重新解析或重试时自动扩大。
- 暂停与取消是不同意图；状态、工作线程和缓存处理三者一致。
- 任务完成指“用户选择的目标完成”，不能用总发现数量直接代替。
- 重试保留哪些设置、何时采用最新登录态，必须在界面和后端保持一致。
- 任务记录只能在工作线程完全停止后删除。
- 不确定的网络提交先核对已有任务，不盲目重发；后续可加入简短的客户端请求 ID 做幂等处理。

可在现有类中完成这些规则，不需要事件总线、消息队列或复杂插件系统。

### 6.2 历史列表先减轻数据量，再考虑更换存储

只读测量时 `/api/jobs` 返回 156 条任务、522,118 bytes，三次请求约为 91.6/108.1/132.7ms。该数据随运行任务变化，不能视为固定性能基准，也没有证据说当前已经严重卡顿。

不过 [home.js:354](<D:/Shiying/app/static/home.js:354>) 已有 SSE 时仍每四秒取完整列表；[main.py:286](<D:/Shiying/app/main.py:286>) 为已完成项目反复检查文件并统计大小，健康检查也会重新计算源码指纹。历史增长后，没必要让普通首页持续承担全部详情与文件检查。

建议：列表仅返回摘要，详情点击时读取；完成时记录结果大小、用户打开文件时检查存在性；SSE 用于活动更新，全量轮询降为断线恢复；历史简单分页。只有测量证明 JSON 文件管理成为瓶颈时，再评估 SQLite。

### 6.3 缓存和磁盘空间是个人用户更直接的维护成本

只读盘点时 `cache` 有 43 个文件、1,214,952,174 bytes，约 1.13GiB。它们可能包含有效的续传数据，**不能直接等同于垃圾，也没有删除它们**。

建议在设置中显示缓存总量、关联的活动/暂停任务，以及可清理的已终止残留。清理前先核对任务引用；允许按任务清理并说明会失去续传能力。环境检查除“能写一个测试文件”外，还应显示目标盘剩余空间；更新、备份和移机时说明哪些目录必须保存。

### 6.4 安全措施应减少用户负担，同时保持现有边界

当前 DPAPI、跨站写入保护和媒体不覆盖属于已有优势。下一步优先补 F08 的新平台边界与凭据生命周期，而不是给本机单人产品增加账户系统。

- Windows DPAPI 凭据绑定用户/机器，复制项目到另一台机器后需要重新登录；移机向导或说明应明确此点。
- “已保存”不等于“仍有效”，登录态状态应区分保存存在、校验通过和失效。
- 自动读取 Chrome 与手工保存凭据的行为应可见、可关闭；不要让用户靠反复退出浏览器猜测。
- 本地 `extension` 目录存在扩展打包用 `.pem`，当前 `.gitignore` 未排除 `*.pem`、`releases/`、`backups/`、`graphify-out/`。恢复 Git 或自动打包时需明确排除私钥、运行快照与敏感备份。该发现不代表这些文件已经对外发布。
- 故障反馈优先导出脱敏诊断：产品版本、平台、阶段、固定错误码、组件版本与耗时。不要让普通用户复制整段播放 URL、Cookie 或原始日志。

## 7. 单人项目的工程管理方案

### 7.1 先建立可回滚的源码事实

当前 `D:\Shiying` 执行 `git status` 返回“不在 Git 仓库中”。这描述的是本机工作目录，不代表上游没有 Git。

建议把源码与本机运行资料分开管理：先确认忽略规则，再恢复或建立一个受版本控制的源码目录。日常只需一个主要工作分支、清晰的小提交、可识别的发行标签；不需要为一个人引入复杂 Git Flow。

每项任务记录五个字段即可：用户问题、范围、验收步骤、优先级、完成证据。完成的定义应是“用户操作通过”，而不是“文件已修改”或“新增测试存在”。本次 F02 的测试直接向 `manager._jobs` 填入项目，绕过了真实 API 的空任务状态，正是验收路径偏离实际使用的例子，见 [test_preview.py:63](<D:/Shiying/tests/test_preview.py:63>)。

### 7.2 测试分成三个层次，避免数量掩盖缺口

| 层次 | 应验证什么 | 最小做法 |
| --- | --- | --- |
| 离线逻辑回归 | URL、安全边界、状态迁移、文件发布、错误映射 | 保留现有 pytest；所有外部网站、用户 Cookie、固定端口依赖显式隔离 |
| 用户操作回归 | 真页面上的预览、选择、暂停、登录等待、错误恢复、焦点 | 少量浏览器流程用例，使用可控 API 与传输夹具；断言实际结果而非只检查元素存在 |
| 真实平台 smoke | 当前站点、账号条件、媒体形态是否仍可用 | 手动或发布前按明确样本执行，保存时间、环境、结果与限制；不把平台限流归咎为代码必然错误 |

当前 CI 有三系统、Python 3.10/3.14 的 pytest 矩阵，这是良好基础。发布所用 Python 3.12 和 Windows 桌面入口也需要对应验证。检查跳过项的原因；前端测试因 Node 不存在而跳过时应明确暴露，不能只看绿色总结果。

本次停止脚本用例没有 mock `_fetch_health`，会读到本机正在运行的 8766 服务；补上隔离后该用例通过。测试必须做到“软件正在运行时也不会错误探测或干扰用户实例”。

### 7.3 只做能减少后续改动成本的拆分

当前规模：`downloader.py` 7,753 行，`task_manager.py` 3,841 行，`app.js` 2,656 行；`home.css` 只有 20 个物理行，却包含整个主界面样式。前两者集中了平台分支与通用流程，后者压缩写法不利于审查与定位。

建议按收益顺序处理：

1. 先让新旧视频号路径共用一个调度与存储约定，解决 F14。
2. 从旧 `app.js` 提取首页实际需要的错误呈现/状态文案；当前首页加载整份文件，但其旧界面初始化随后直接返回。删除前确认旧测试和旧页面是否仍需要它。
3. 将新加的平台适配放在现有独立模块中，公共传输只负责进度、取消、校验和发布。逐次迁移并保留回归，避免一次拆散全部抖音逻辑。
4. 格式化主界面 CSS，减少一行数千字符的维护成本；统一文字、状态和主题变量。
5. 不急于引入依赖注入框架、分布式任务系统、微服务或大型前端状态库。

### 7.4 发布过程应能在干净目录复现

当前已有两个 0.1.0 ZIP，但没有与最新功能一致的权威发行记录；多个文件继续使用上游 1.3.0。建议一个简单发布脚本完成：检查版本 → 跑必要测试 → 按白名单打包源码/静态资源/启动入口 → 输出校验值与版本记录。

发布前至少在空目录验证一次安装与启动，不依赖本机已经存在的 Python 包、缓存和登录态。依赖或 Chrome/FFmpeg 故障要给可执行的修复说明；不要要求普通用户自行看完整 server.log。若只服务这台 Windows 机器，先把 Windows 安装/升级做稳，再决定是否承诺跨平台桌面支持。

## 12. 适合这个项目的完成标准

一个人打开拾影，能在不理解端口、Cookie 文件、线程状态或下载器内部结构的情况下，完成“保存想要的内容，找到结果，处理失败”。维护者能用一份安装说明、一个依赖来源、一条可信的回归流程和一份有版本的发行记录持续改进它。

用这个标准衡量，当前最有价值的投入是修好已有流程、减少重复入口与矛盾文档、让失败可解释且可恢复。搜索、文件打开与缓存管理随后补充；更多平台与媒体后处理能力放在这些基础稳定之后。
